# Day 29 素材｜把 unverifiable、mismatch 兩行定義寫窄，能不能放行

Day 17 的決定：多標 115 個裡 104 個落在 `unverifiable` 與 `mismatch`，這兩行定義寫得最鬆，
所以往 precision 讓，把這兩行寫窄，界線是 recall 不掉破七成。這份文件記下改之前定好的成功條件，
跑完之後在下面補結果。成功條件這一段在跑任何一批之前 commit，commit 時間就是「事先」的證據。

## 改動

`prompts/narrow-definitions.txt`：只動 `src/agent/prompt.ts` 裡三類問題下面的兩行，其他一個字不動。

- unverifiable：從「這條 AC 沒有寫清楚怎樣算做完」改成只算用形容詞描述、寫不出可觀察行為或數字的 AC
- mismatch：從「這條 AC 跟 description 說的不一樣」改成要跟 description 裡某一句相反或對不上才算，
  description 沒提到的不算（Day 17 文中舉的寫法）

## 成功條件（改之前寫下）

比法照 Day 28：原版與窄定義版同時開跑、各兩批、每批 16 筆 × k=5、`--fill-missing`，
成對比較（同時開跑的兩批配一對）。某個差距要算「改動造成的」，兩組配對方向必須一致，
而且兩組差距都要大於兩邊各自同 prompt 兩批之間的差距。

1. **precision 真的升，而且升到 50% 以上。** 兩批窄定義版的 precision 都要 ≥ 50%，且照上面的比法
   判定為真的變好。50% 的意思是看卡的人每讀兩個標註有一個是真的；Day 17 說 34%（每三個一個）
   已經在被放棄的邊緣。
2. **recall 不破七成。** 兩批窄定義版的 recall 都要 ≥ 70%。這是 Day 17 先訂下的界線。
3. **門檻照 Day 27。** 16 筆 case 各跑 5 次、次次通過，pass^5 要 16/16 才放行；有缺趟的 case
   記為評估未完成，同樣不放行，跟判定失敗分開列。這一條由 `run-all` 自己印出擋或放。

1、2 都成立，叫做「診斷變好」，可以把窄定義併進 `prompt.ts`；3 成立才叫「放行」。
兩者分開判：診斷變好但門檻沒過，結論是定義可以收、這一版仍不放行。
